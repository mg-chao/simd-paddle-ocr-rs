# Step 2: complete tiny scalar OCR performance

On one upright 350×140 four-line page, the median of six process p50 values was **415.71 ms for Rust owning OCR and 497.13 ms for C#**. Rust borrowed OCR measured 340.56 ms in its separate process series. The structured Step 2 report (local `docs/tiny-ocr-performance.json`) retains every process, cold boundary, allocator record and binary/model identity. The result applies to this scalar page and protocol.

Each complete call starts from frozen raw BGR pixels and includes DET, boxes/crops, CLS/orientation, pixel REC preprocessing, compact recognition, CTC and alignment. Owned Rust calls also convert and drop the result; C# creates its public owning result. Image decoding, loading and preparation are outside warmed inference. Borrowed OCR is Rust-only. The full diagnostic REC graph is a separate workload: its Rust/C# median process p50 values are **406.15/352.52 ms**, so the owning OCR result does not imply a universal kernel or graph advantage.

All values below are milliseconds, using six fresh processes per engine/mode, 30 warmups and 100 page samples. Engine order alternates across paired rounds. Medians summarize the six process p50/p95 values; ranges show observed process extrema rather than confidence intervals.

| Measured scope | Engine | Median process p50 | p50 range | Median process p95 | p95 range |
| --- | --- | ---: | ---: | ---: | ---: |
| Complete page, owned result | Rust | 415.71 | 309.08–468.10 | 540.14 | 347.62–839.86 |
| Complete page, owned result | C# | 497.13 | 370.48–556.17 | 733.39 | 605.60–803.94 |
| Complete page, borrowed result | Rust | 340.56 | 326.48–412.35 | 451.66 | 362.25–479.73 |

Collection used Windows x64, Rust 1.97.1, a reported Ryzen 9 5950X, 24 process-visible processors and the Balanced power plan. Rust uses serial scalar kernels without explicit SIMD; C# uses NCHW with hardware intrinsics, fusion, tiered compilation and tiered PGO disabled and one worker. No CPU affinity or dedicated machine was used. A background linker burst was observed and all six runs were retained. Rust owning p95 values ranged 347.62–839.86 ms; this process variation remains part of the result. Linux gates are correctness/allocation checks, not a paired Linux latency study.

Three separate allocator processes measured zero warmed allocation count, allocated bytes, retained growth and peak growth for borrowed OCR. Owning OCR allocated **55 times and 3,022 bytes per page**, with no retained growth after drop. Its isolated completed-view copy/observation/drop probe took about **2.6 µs** (six processes, median p50; pooled p95 2.9 µs), excluding inference, preprocessing and creation of the borrowed result. It copied joined text, four line records, their text, and 45 token spans/strings. Separately collected owning and borrowed medians cannot be subtracted to estimate this cost.

The whole-page reuse probe (local `docs/ocr-storage-performance.json`) ran upright→rotated→blank→1×1→upright using one mutable OCR engine per process. After two capacity cycles and three warmup sequences, three processes each measured three five-page sequences: **45 page calls, with all four allocation counters zero**. Native public fields were checked before warmup, including the two empty results. This is allocation evidence, not a latency study. It requires enough capacity for shape plans, activations, resize buffers, detector/crop storage, decoded text and spans; unseen larger images/results may grow storage. The native Linux supplement (local `docs/ocr-linux-allocation.json`) separately passed the three-line REC/two-line OCR selections, now local-only, and warmed borrowed/mixed-width allocation smoke checks.

These are requested storage sizes, excluding shared weights, allocator overhead, owned output copies and process RSS. Diagnostic workspace is already included in workspace; result budgets count active bytes/records rather than retained spare capacity. Session activation budgets do not cap combined pipeline RSS or transient old/replacement buffers. Official owning-mode RSS ranges were 27.70–28.06 MB for Rust and 85.08–89.07 MB for C#, including runtime/corpus preparation; differing retention and runtime boundaries prevent a paired memory ratio.

Cold loads, preparation and first-call costs are separately recorded. Rust imports DET/CLS during OCR preparation whereas C# does so during loading; these totals are not directly comparable startup benchmarks. First calls include inference and possible growth. Prepared full-session rebind probes are separate from OCR: their **0.30825 ms** value covers two 992→224→992 reshapes with regrowth zero-fill, not recognition or one metadata-only resize. The tiny 0.5 µs synthetic compaction timer is near clock granularity and is not a real OCR memory-compaction result.

Retained scalar tuning (local `docs/tiny-rec-tuning.json`), compact projection tuning (local `docs/tiny-rec-projection-tuning.json`), and remaining scalar evaluation (local `docs/tiny-rec-scalar-evaluation.json`) preserve their own isolated scopes. The final node profile observes the dense REC graph; its operator percentages cannot be treated as full OCR/public-head fractions. Tested rectangular depthwise and blocked Transpose variants produced no repeatable benefit, so production code was retained; existing resize row caching also remained. No isolated ratio is promoted to an end-to-end gain.

Final complete parity (local `docs/tiny-ocr-parity.json`) passed on Windows and Linux across four source cases, 32 detected recognition lines and **9,761 artifacts**; REC separately covered all 5,248 required artifacts. Ordinary tests total **143 Windows / 140 Linux**. Harness hardening (local `docs/rec-harness-hardening.json`) occurred after official timings; inference APIs/kernels/benchmark sources are unchanged, and final native gates were rerun. The 47-file correctness digest is `e8765aec83e8ae64429464b4567cae4f39a143d9f7096c766a0f593d1a32c6e1`; 45 files match the prior proof, while REC validation and its tests changed. Evidence archives (local `docs/tiny-ocr-evidence-archives.json`) retain the distinct proof/storage snapshots. No remote CI execution or general OCR accuracy/speedup claim follows from these measurements.
