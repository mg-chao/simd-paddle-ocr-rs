## Pipeline and bottlenecks

`OcrModelSet` reads local ONNX files and dictionaries. Normalization folds eligible graph patterns. The builder validates each graph and its shapes, prepares packed coefficients, and constructs an immutable plan. An `OcrRequest` holds its own activation arena, crop buffers, width-specific sessions and decoding state. `OcrEngine` leases requests from a bounded pool. Normal pages can borrow input pixels. Extreme aspect ratios may require resize or padding. Detector preprocessing writes resized pixels into the selected layout. Bound CPU kernels, layout conversions and SIMD dispatch execute DET. DB thresholds the map, processes contours and returns ordered quadrilaterals. Perspective crops and optional orientation classification produce the recognition inputs.

Six-crop aspect-ratio groups determine the recognition canvas. The scheduler assigns width-aware jobs to worker sessions and can batch equal widths. The default probability path projects to the vocabulary and skips softmax on proven blank rows. CTC decoding produces text, scores and optional spans. The request restores coordinates and joins the lines. Optional paragraph grouping consumes assembled lines. The resident GPU path uses a page upload, device-side detection and crop preparation, bounded recognition waves, and compact result readback. Submission completion governs buffer reuse.

On the primary page the initial small diagnostic spent 271.398 ms in recognition, 145.992 ms in detector inference, 8.983 ms in classification, 3.966 ms in cropping, 2.473 ms in DB and 0.099 ms in result storage. Eight recognition owners processed 25 lines. Worker times overlap. The initial cold plan cost reached 69.010 ms on medium. This prioritized matrix work, graph compilation and weight packing ahead of result copying.

## Round ledger

CPU times in each triple are tiny / small / medium. Every integrated CPU candidate has six frozen public JSON captures, three timed requests and one warm-up. Rounds without a production edit reuse the indicated baseline's public correctness and timings. Each source patch and full SHA-256 is in the corresponding raw summary. The short identifiers below are SHA-256 prefixes of the patch against the initial commit.

1. **Reuse wide AVX2 vocabulary panels.** The 6,906- and 18,710-class heads can reuse a packed panel across six-row tiles. A previous local test at the same commit had inconclusive six-line page timings. I applied its selector change to the public MatMul path and screened this 25-line page. Focused pointwise tests on both frozen source versions each passed 23 tests with four ignored. All six aligned outputs matched exactly, including irregular vocabulary tails. Initial → R1 (`66713cb9367694e9`) was 120.216 → 118.294 / 545.644 → 532.957 / 1944.294 → 1939.570 ms. Separate small stage profiles were captured. Reverted because the 0.2–2.3% reductions were below threshold. Next examined cold convolution packing.
2. **Transpose convolution weights in 4×4 tiles.** Output-major coefficients are repacked into K×16 panels. A SIMD transpose could reduce strided loads while preserving incomplete tiles. An isolated release build of the actual packing module checked arbitrary bit patterns at 80 dimension pairs. One call per variant for each representative shape, opposite ordering on the second shape, zero warm-ups and 10-second process timeout. Scalar → trial was 0.3513 → 0.2748 ms at 384×768 and 1.2886 → 1.3212 at 768×1536. Every element matched. The larger matrix lost time. Rejected before integrating, so the initial public results apply. Next examined row-major packing.
3. **Specialize the complete vocabulary panel copy.** The inner loop copied a variable number of coefficients even when a full 16 were available. The trial kept the tail handling and copied complete panels at fixed width. The same 80 shape checks passed. One small and one medium vocabulary pack per version took 3.4509 → 2.6882 and 4.5711 → 3.9956 ms. All six public captures matched. Initial → R3 (`36fc92566dddaab2`) plan creation was 3.247 → 6.243 / 15.811 → 15.333 / 69.010 → 88.243 ms. OCR was 120.216 → 120.130 / 545.644 → 568.144 / 1944.294 → 2177.504 ms. The packing savings did not survive full startup. Reverted. Next isolated graph validation.
4. **Vectorize the coefficient finite-value check.** A 32-element SIMD mask plus a scalar tail scans every constant while preserving the nonfinite error. The probe checked every invalid position at eight boundary lengths for NaN and both infinities. One scan per implementation on each normalized detector took 0.2027 → 0.0326 / 1.1584 → 0.6437 / 7.2328 → 3.1402 ms. All six public captures matched. Initial → R4 (`ddfa104e48591d00`) plan creation was 3.247 → 19.848 / 15.811 → 41.118 / 69.010 → 136.115 ms. OCR was 120.216 → 458.354 / 545.644 → 1211.651 / 1944.294 → 3685.552 ms. Even medium model loading, outside the modified function, nearly doubled during the trial. Reverted because public startup could not be qualified under those conditions. Next tested file buffering.
5. **Increase the file buffer for large ONNX payloads.** The importer used 64 KiB even for a 76 MB recognizer. With the order reversed for small, one actual REC import per buffer size took 3.971 → 3.749 / 16.367 → 14.246 / 45.213 → 40.730 ms at 64 KiB → 1 MiB. Graph counts and normalized weight sizes agreed. R5 (`875e36503e3edee1`) applies the larger buffer to files of at least 8 MiB. All tiny assets use the original buffer. File limits and streaming fallback are preserved. The six public JSONs matched. Initial → R5 model-set load was 8.587 → 8.700 / 23.379 → 25.165 / 94.618 → 82.233 ms. OCR was 120.216 → 109.113 / 545.644 → 420.814 / 1944.294 → 1601.579 ms. The contradictory small load screen prompted a bounded A/B, B/A startup-only check. One binary opened, parsed and normalized all four assets through the public reader factory, with two pairs per affected preset, zero warm-ups and 15-second timeout. Small control → trial was 29.633 → 25.323 and 28.316 → 23.077 ms. Medium was 86.229 → 83.518 and 100.731 → 84.968 ms. Retained for model loading. Next examined concurrent graph compilation.
6. **Compile the two independent CPU stages concurrently.** The detector and recognizer previously compiled in sequence. One serial and one parallel compilation per preset on the existing eight-worker pool (15-second process timeout, order reversed for small) took 2.324 → 1.742 / 13.561 → 11.264 / 61.328 → 41.463 ms, with equal packed byte counts. R6 (`a380a11312a7c5b5`) uses a two-task join for CPU targets when the builder owns the compiler and the pool has capacity. Detector errors retain priority. Explicitly shared compilers, serial contexts and mixed targets keep sequential execution. Three builder tests passed. All six public captures matched both R5 and the initial version. R5 → R6 plan creation was 3.072 → 3.093 / 15.614 → 12.469 / 62.841 → 41.175 ms. OCR was 109.113 → 116.995 / 420.814 → 438.455 / 1601.579 → 1596.129 ms. Retained for startup. Next checked the scope for optimizing branch-weight generation.
7. **Linearize branch-weight accumulation.** A linear slice addition could replace centered kernel indexing when branch extents match, provided the addition order and padding stay exact. I queried the seven normalized production graphs to count surviving generated branch weights. Only medium DET had any, with 12 tensors and 339,968 coefficients (1.36 MB of 61.45 MB of normalized weights). All six other graphs had zero. The census measures result size and does not time transient normalization passes. No production change or timing was warranted for this narrow arithmetic path. R6 public results apply. Next examined repeated recognition features.
8. **Project bitwise-identical recognition rows once.** A production-prefix replay used the three most heavily padded retained lines per preset on the timing page, matching crop geometry and content width against the frozen output. The three small matrices had 69, 72 and 79 distinct rows out of 205. Medium had 75, 76 and 80 out of 234. R8 (`7c754a3df4a613b8`) identified the longest consecutive identical run in plain packed AVX2 MatMul, projected its first row and copied the logits. A focused test covered leading, interior, trailing, full and absent runs, signed zeros and partial vocabulary panels. Isolated sessions replayed the real weights and features for the most padded crop per preset. One call each, zero warm-ups and 15-second timeout per process. R6 → R8 was 3.5373 → 4.9580 / 14.9786 → 12.8925 / 30.8045 → 23.0010 ms. All output logits matched bit for bit. Tiny had only 27 duplicates out of 247 rows. Splitting that GEMM was costly. All public captures matched but OCR was 116.995 → 117.408 / 438.455 → 553.193 / 1596.129 → 1517.265 ms. The small regression and modest medium improvement failed the gate. Reverted. A separate small profile was captured. Next tested a width-only cutoff.
9. **Skip projected time steps past the content boundary.** An offline replay discarded columns from ceil(steps × content_width / tensor_width) onward. Across the timing page this would skip 435 / 1,016 / 1,146 steps without crossing any captured span. On the second page tiny and small each emitted a token in [35, 36) when the proposed cutoff was 35. This would change text and alignment. Rejected after six JSON replays, before code or timing. R6 public results apply. Next inspected GPU transfers.
10. **Remove a possible dense GPU readback.** Six actual GPU calls used the adapted `gpu_ocr_bench`, explicit FP32, classification batch four, recognition batch and wave one, one slot, one worker request, and alignment. One fresh second-page correctness call per preset preceded one fresh timing-page call per preset. Zero warm-ups or internal repetitions. The timer includes the harness thread launch and owned conversion, and excludes decoding, startup, serialization, character-box computation and diagnostic collection. All six reported Resident on the discrete RX 6750 XT, Vulkan driver 26.11.2. On the timing page each uploaded one 3,147,264-byte RGB image. Projection and decoding ran on GPU with zero CPU compute stages and zero diagnostic readback. Output readbacks were 42,976 / 57,120 / 62,376 bytes plus 688 / 616 / 616 control bytes. The code already transfers compact token and classification records. All six texts agreed with CPU. GPU control was 89.344 / 653.216 / 702.415 ms. No dense transfer to remove. The 28 / 27 / 27 submissions justified testing wider waves.
11. **Put two independent recognition units in each Vulkan wave.** Only the wave limit changed. The same executable, inputs, precision, batch sizes and timing boundaries were used. All six resident outputs, CTC spans and character boxes matched the GPU baseline exactly. Wave one → two was 89.344 → 90.097 / 653.216 → 226.881 / 702.415 → 685.589 ms. Each preset dropped to 15 submissions. Peak device bytes were equal, but retained storage grew by 4.58 / 13.57 / 23.66 MB. To test whether the apparent small win persisted after both driver paths had been exercised, one reverse-order pair was run on small (15 seconds per process). Two-wide took 221.745 ms and one-wide took 220.691 ms, with identical outputs. The submission reduction was confirmed and the latency gain was inconclusive. Kept the existing default. Each setting had three correctness calls, three timing-page calls and one small reverse-order check. Next tested CPU owner count.
12. **Trade recognition owners for intra-op threads.** R12 (`0c3e3476911b635f`) assigned four owners with two threads each to dense automatic eight-thread Windows AVX2 requests with at least 16 recognition units. Detector, classifier, width selection, graph batch size and explicit worker settings stayed fixed. The focused ownership/order/recovery test passed, and all six public captures matched the initial version and R6. A separate small profile per setting confirmed eight → four owners but measured 367.462 → 367.661 ms recognition wall. Public OCR was 116.995 → 129.630 / 438.455 → 510.347 / 1596.129 → 1827.215 ms. Reverted after one screen. R6 is the final version.

## Reproduction and scope

From the repository root, these commands inspect the raw measurements and run the frozen public entry points. The local evidence directory holds the exact binaries used, the starting source archive, model and input manifests, trial patches, aligned JSON, operator replays, GPU placement statistics and the adapted example sources.

```powershell
$r = 'reports/ocr-exploration-12'
$images = Get-Content -Raw "$r/inputs.json" | ConvertFrom-Json
Get-Content "$r/initial/latency.tsv", "$r/r06/latency.tsv"
Get-Content "$r/load-pair.txt", "$r/compile-pair.txt"
Get-Content "$r/gpu-control/summary.json", "$r/gpu-wave2/summary.json"
& "$r/initial/ocr_exploration_latency.exe" $images[0].input
& "$r/r06/ocr_exploration_latency.exe" $images[0].input
& "$r/r06/ocr.exe" --execution cpu --threads 8 --preset medium --alignment $images[1].input
cargo test --release --locked --lib
cargo test --locked --no-default-features --lib builder::
cargo run --release --locked --features profiling --example rapidocr_parity_latency -- $images[0].input
```

To rebuild the cold-start measurements in a disposable checkout, start at the recorded commit, apply the selected `source.patch`, and place the archived `ocr_exploration_latency.rs` under `examples/`. Build with `cargo build --release --locked --features profiling --example ocr --example ocr_exploration_latency` and run from a directory with the nine matching assets under `../SimdPaddleOCR/models/`. The original latency example uses the same request boundary. GPU reproduction uses the archived GPU example and `gpu_run.py` with explicit device placement and no internal repetitions.

Correctness coverage is two pages and request timing is one page on one workstation. Ordinary desktop activity and driver first-use costs were visible. The results do not establish disk-cold startup, a sustained throughput or latency distribution, concurrent production performance, or behavior on other CPU architectures or Metal. Optional paragraph inference was outside the measurement set. The Windows OCR example linked with the existing LNK4098 CRT warning and completed every capture.
